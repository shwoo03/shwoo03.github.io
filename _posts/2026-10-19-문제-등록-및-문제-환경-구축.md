### 계획
{: id="계획"}

CTFd 가 아닌 곳들도 많고 바로 CTFd 크롤링해서 자동 풀이 시작하는 곳도 있는데 이거는 별로 그렇게 하고싶지 않아서 로컬 UI 에서 등록할 수 있고 등록하면 바로 자동적으로 문제 풀이 가능하도록 설계함

크롬 분할 탭을 활용해서 문제 등록을 빠르게 가능하게 하고 첨부 파일은 최근에 다운로드한 파일을 자동으로 감지해서 빠르게 내가 드래그 앤 드랍 안해도 빠르게 등록할 수 있게 할것임.

#### 최근 다운로드 파일 자동 선택
{: id="최근-다운로드-파일-자동-선택"}

python 이 크롬 다운로드 폴더를 폴링하면서 확인하고 최신 파일을 웹 UI 에서 체크 가능하도록 하면 됨.

그리고 크롬 다운로드 디렉터리는 WSL 안으로 설정할것임 굳이 다운로드 받고 다시 윈도우에 있는 파일을 WSL 로 복사하는 과정을 거치지 않아도 되기 때문임.

요구 사항은 다음과 같이 설정함

- 파일 감지: 1초 간격
- 파일 검색 범위: 최근 10분
- 표시 개수: 최대 10개
- 자동 체크: 가장 최근에 다운로드된 파일 1개
{: .notion-bulleted-list-item}

```plaintext
/home/user/ctf-auto-solver/
│
├── inbox/                    ← Chrome 다운로드 경로
│   ├── babyheap.zip
│   └── libc.so.6
│
├── backend/                  ← Python FastAPI
├── frontend/                 ← Quick Intake UI
│
└── challenges/
```

그럼 프로젝트 구조는 대략 다음과 같을 것임 그리고 문제를 등록하면 다음과 같이 inbox 안에 들어감

```plaintext
ctf-auto-solver/
└── inbox/
    └── .staging/
        └── babyheap-a83f2c/
            ├── original/
            │   ├── babyheap.zip
            │   └── libc.so.6
            │
            └── intake/
                ├── input.json
                └── raw-description.txt
```

테스트 중에 문제가 발생했다;; 윈도우에서 다운로드 받은 파일에는 Zone.Identifier 라는 것이 생기는데 인터넷에서 다운로드한 파일에는 다음과 같은 문자열이 파일명에 붙음. 따라서 이거를 제거할 수 있는 방법이 필요하다.

#### luna 동작
{: id="luna-동작"}

위의 프롬프트를 받아서 luna 모델은 다음과 같이 정형화된 문제 지문을 만듦

```plaintext
{
  "points": 500,
  "description": "Exploit the heap vulnerability.\nYou may need the provided libc.",
  "connections": [
    {
      "protocol": "tcp",
      "host": "52.79.35.14",
      "port": 31337,
      "command": "nc 52.79.35.14 31337"
    }
  ],
  "flag_format": "flag{...}"
}
```

해당 응답을 할 때 cli 옵션에 <strong><code>--output-schema</code></strong><strong> 등의 옵션을 활용해서 응답에 적용할 JSON 구조 등을 지정해서 응답을 JSON 형태로 강제할 수 있음 물론 그럼에도 가끔 이상한 짓을 해서 조금 이상한 형식으로 변형되거나 형식이 깨질 수 있지만 재시도 로직으로 커버 가능하다고 생각함 그리고 뭔가 복잡한 JSON 이 아니라 간단하거라서 괜찮다고 생각함 (로깅 하면서 에러율이 높으면 개선해야할듯..)</strong>

JEV를 써볼까도 생각해봤지만… 결국 내가 하려는게 이상한? 출제 지문을 가지고 있는 문제도 다 커버할 수 있게 하려고 하는것이고 JSON 구조가 정형화되지 않고 바뀔 수 있는 구조가 많아서 적절하지 않다고 생각함

#### python 코드로 yaml 파일 만들기
{: id="python-코드로-yaml-파일-만들기"}

이제 반환된 json 을 기반으로 challenge.yaml 을 생성한다. 이후 challenges 디렉터리로 이동한다.

```yaml
schema_version: 1

id: babyheap-a83f2c
name: BabyHeap
category: pwn
points: 500

description: |
  Exploit the heap vulnerability.
  You may need the provided libc.

connections:
  - protocol: tcp
    host: 52.79.35.14
    port: 31337
    command: nc 52.79.35.14 31337

flag_format: "flag{...}"

attachments:
  - filename: babyheap.zip
    path: original/babyheap.zip
  - filename: libc.so.6
    path: original/libc.so.6

raw_description: intake/raw-description.txt

status: READY
```

이후 기존 임시 디렉터리에 있던 파일들이 자동으로 challenges 디렉터리로 이동하여 다음 단계로 감

```yaml
ctf-auto-solver/
├── inbox/
│   └── .staging/
│
└── challenges/
    └── babyheap-a83f2c/
        ├── challenge.yaml
        ├── original/
        │   ├── babyheap.zip
        │   └── libc.so.6
        └── intake/
            ├── input.json
            └── raw-description.txt
```

여기까지가 문제 등록의 끝이고 다음에는 4개의 에이전트로 문제를 해결하고 skill 지정 및 mcp 및 docker 환경 세팅을 자동화하는 방법을 생각할것임. 또한 모델이 문제를 해결하면서 중간중간 사용자가 어떤 과정에 도달해있고 중간에서 메시지를 넣을 수 있도록 해줄것임.

까지인데…… 하 생각해보니까 고성능 LLM 이 어짜피 문제를 해결할 때 다시 저 정보들을 읽을 껀데 파싱을 해서 정리할 필요가 없었음 그냥 제목, 분야, 문제 지문 통으로 주고 알아서 해결 하라고 하면 되고 나는 에이전트용 환경이랑 스킬, mcp, docker 환경만 잘 구축해주면 됨;;

일단 이런거를 처음 만들어봐서 다른 블로그나 오픈소를 참고해봤는데 해당 프로젝트는 여러 AI에게 미리 역할을 나눠주고 AI들이 발견한 사실과 다음 탐색 방향을 하나의 그래프 형태로 공유하면서 문제를 해결하도록 만든 시스템임 해당 프로젝트는 장시간 탐색해야 하는 CTF, 취약점 분석, 수학 문제를 대상으로 설계됨.

![image-3](/assets/img/notion/3feeaafee12e80508923d36d526170cc/image-3.png){: w="2918" h="1584" }

이런식으로 해서 100만 토큰 이상이 필요한 고난도 작업에서 76.5%의 더 빠른 비율을 보여주었고 최대 속도 향상도 관측된것으로는 약 3배가 나옴 단 쉽고 빠르게 해결 가능한 문제는 오히려 단일 AI가 유리하다는 측정이 나옴.

해당 프로젝트에서는 다음 세 가지의 개념이 나옴

- Fact → 조사해서 알아낸 정보
- Intent → 앞으로 조사할 내용
- Hint → 사람이 제공하는 지침
{: .notion-bulleted-list-item}

여기서 각 Intent 가 생성되고 해당 결과로 나온 Fact 가 다음 작업을 위한 Intent로 결합되어서 사용이 됨. <br>즉 하나의 에이전트가 XSS 취약점을 발견하고 하나의 에이전트가 CSP bypass 가 가능하다는 것을 발견하면 해당 결과는 다음 작업을 결정할 때 결합되어서 수행된다는 것임. 또한 해당 프로젝트에서는 Web 전문가, Pwn 전문가 처럼 고정된 분야별 역할을 필수적으로 두지 않고 각자 작업을 부여받으면 단일 에이전트처럼 동작해서 초기 빠르게 해결할 수 있는 문제는 굳이 공유하는 로직을 갖지 않고 동작하게 함.

그리고 각 발견의 결과는 모두 하나의 공용 저장소에 저장하고 에이전트가 하나의 에이전트 작업을 인터럽트 시키지 않고 저장한 후 에이전트들이 하나의 작업이 끝나면 알아서 결과를 보고 다음 행동을 하는 방식임.

근데 논문에서 단일 AI와 해당 프로젝트의 방식을 비교했을 때 10만 \~ 100만 토큰의 작업은 단일 AI가 더 빠르게 해결했음. 연구진은 124만 토큰 이상이 소비되는 문제를 해당 프로젝트로 해결하는 것이 효과적이라고 판단함.

정보를 짧게 전달하는 것만 하는게 아니라 구조화된 정보 제공 양식을 정해서 연구를 했다고 하고 멀티 에이전트 실험 토큰 절감은 38.7%, SWE-agent 입력 토큰 절감 50.4%, OpenHands 문제 해결률 3.5% 상승, SWE-agent 해결당 토큰 절감 47% 인데 해결율은 1.4% 하락함.

해당 연구에서 제시한 문제점은 멀티 에이전트 시스템에서는 같은 정보가 여러 번 입력으로 들어간다는 것임 이렇게 되면 LLM이 30분 정도 생각하다가 나온 결론을 다 다음 에이전트 입력으로 넣는것 보다는 중복을 제거하고 구도화해서 최적화해서 다시 입력을 만드는 것이 필요함.

그래서 연구진은 이것저것 테스트 해봄 전체 출력을 공유하는 방식, 짧게 답변하도록 유도하는 방식, 자유 형식 요약 전달 등등

결론적으로 연구진이 제시한 알고리즘은 Action - State - Result 임

- Action → 수행한 작업 및 다음 에이전트에게 요청하는 작업
- STATE → 도구 출력, 관찰한 사실, 실험 결과, 환경 상태
- RESULT → 발견된 정보, 만들어진 결과물, 확인된 결론
{: .notion-bulleted-list-item}

이런식으로 구조화하여 전달하면 긴 설명을 읽지 않아도 어떤 결과가 나왔고 그 근거는 무엇이고 무엇을 해야하는지 효과적으로 결정할 수 있다고 함 그리고 미검증된 것들은 확실하게 미검증으로 표시하면 할루시네이션이 줄어듦

근데 여기서도 문제는 있음 결국 정보를 정리하고 제공하는 것도 에이전트가 하는거라서 요약하다가 중요한 정보가 없어질 수 있고 에이전트 도구 출력까지 최적화하지는 않음. 그리고 장시간 분석이나 복잡한 문제를 해결할 때는 검증되지 않았다고 함.
